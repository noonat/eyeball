Widening

Three steps out from a hunk, each one control rather than a navigation. A diff often refers to something it does not contain, and walking to a computer to look it up ends the review, so every file is reachable as the agent had it. That costs no extra storage: the capture holds what the agent changed, and git already holds what nobody touched.

Foundations Queue Review Widening Project Readme

Step one: the hunk where reading starts

The change with enough surrounding lines to make sense of it, read in its file card on the review page. The Whole file icon in the card’s header is the step out. A reference the hunk cannot show is a link rather than a note telling the reviewer to go and look.

  • The link out is in a notice, not buried in the code. A tappable identifier inside a monospace line is a target about eight pixels wide, and the line has to keep its column alignment.
  • The step out lives on the card, not on a page of its own. The review page already shows each file’s hunks in its card, so a second page holding one file’s hunks would only repeat them.

Step two: the whole file change still marked

The same file with everything around the change, and the change still tinted in place. Marked and Plain switch the tint off, for reading the file as the agent left it rather than as a change.

  • The counts stay in the toolbar and say what they count. Out of the diff, a bare pair of numbers reads as a property of the file rather than of the round.
  • The path truncates from the left. Directories are what repeat across a project; the filename is what identifies this one.

Step three: any file at that round context, not change

A file the review does not touch, opened because the change refers to it. It carries a banner saying so, and the reason is not politeness: a file opened for context looks exactly like a file under review, and a reviewer who confuses them either approves something unread or comments on something unchanged. The banner also says which context it is, because a file can arrive from three places and only two of them are exact.

  • Nothing extra is stored to make this work. A capture holds the base commit and the files that differ from it. A file the agent never touched is byte for byte what the base commit already holds, so it comes out of git and costs nothing. A file the agent did touch is in the capture, in scope or not. Either way the reviewer sees what the agent had.
  • Three sources, three banners. The capture is frozen and needs no banner beyond saying the file is not under review. The base commit is exact, and says so. The working copy is neither, and warns rather than informs, because it is the one a reviewer can draw a wrong conclusion from.
  • The live fallback exists so browsing never dead-ends. A reviewer who cannot look up a definition goes to a computer, and the review ends there. A labeled approximation beats a blank page, and this is the only place in the surface where that trade is taken.
  • A file under review never comes from the working copy. It is always in the capture, so no verdict is ever given against a live reading. That boundary is what makes the trade above acceptable.
  • A file this surface cannot render says so. An empty panel reads as a failure to load, and the reviewer retries it.

Files a browser can display page, image, neither

Reading every file as text makes the surface useless for whole categories of work. A design mockup is an HTML file, and reviewing one means looking at the page. So is a chart, an icon, a screenshot on a bug. Markdown already renders; this is the same rule applied to everything else that has a rendering.

  • A page an agent wrote is a program, and it renders in a sandbox from another origin. Without that, a file in a review can read the queue, post comments and approve itself, and the agent that wrote it has every reason to. The frame says so rather than leaving it to be assumed, because the reviewer is about to trust what is inside it.
  • SVG belongs on the page side of that line, not the image side. It is a document format that can carry script and is routinely filed with the image formats. Shown through an image element it cannot execute. Opened as a page it can.
  • Before over after, at one width. Two images across a phone screen are two thumbnails, which is the same reason diffs are unified. The tint on each frame is the diff palette, so the pair reads the same way a changed line does.
  • Dimensions and bytes are on the caption of each. Half of what a reviewer wants from an icon change is whether it got bigger.
  • A file that is neither says what it is and stops. Its kind and its size are what the reviewer was actually asking, and a download onto a phone is not something anybody reviews.

A file that changed mode, opened the same line, on its page

The file page carries the card's mode line at the top of the file, so the change is stated wherever the file is read.

Images, recordings and documents new, deleted, played, framed

The rest of what a browser displays, each in the frame the page and the changed image already use. A recording plays in place. A PDF shows in a frame with Open beside it, because how a phone draws a PDF inside a page is the one thing here a tearout cannot show; the phone check decides which survives.

  • A new file has only its After, and a deleted one only its Before, captioned New and Deleted in the same tints, so a lone frame still says which side it is.
  • SVG opens as source and flips to Image. It shows through an image element, where its script cannot run, so it gets the image’s before and after. A size alone captions it, since an SVG’s dimensions are whatever its viewBox says.
  • Players fetch only headers until one is played, so a review with six recordings costs six small requests to open. Video plays inline rather than taking the screen.
  • Open is the frame’s one control. It opens the same file as a page of its own, still under the sandbox, for a page or a PDF that wants the whole screen.

Browsing, and the file that will not render two states

The tree is the project at the round under review. Files the review changes are bold, so browsing for context never loses track of which files the verdict is actually about.

  • Changed files carry their counts in the tree. It is the same information the file list on the review page carries, in the one place a reviewer might otherwise lose it.
